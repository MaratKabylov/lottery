# EventDraw

Регистрация гостей и публичные розыгрыши призов. Реализация следует [Architecture.md](Architecture.md): React / Vite / TypeScript strict / Tailwind / React Router / TanStack Query; единственный backend — Supabase. Отдельного API-сервера нет.

## Что реализовано

- Вход через Supabase Auth, роли `admin` и `host` из `profiles`, ограничения маршрутов и серверные проверки прав.
- Создание мероприятий, список, настройки, активация, завершение и архивирование.
- Регистрация через Edge Function, нормализация казахстанского телефона, повторная выдача прежнего билета, транзакционный счётчик билетов.
- QR регистрации, скачивание PNG, мобильная форма, экран с номером.
- Опциональный виджет Cloudflare Turnstile: передача токена в Edge Function, блокировка отправки до проверки, обработка истечения токена и повтор после ошибки без потери полей формы.
- Список участников, поиск, фильтры, активация / деактивация, check-in / отмена по номеру и телефону, тестовые участники 10 / 50 / 100 / 500.
- Создание и изменение призов, количество, порядок, отключение, загрузка изображений и логотипа в Storage.
- Серверный выбор победителя, подтверждение и отмена, контроль остатков, блокировка мероприятия, один незавершённый розыгрыш на мероприятие.
- Панель ведущего, большой экран без авторизации, Realtime и восстановление состояния из БД, анимация по серверному времени, конфетти, звук после действия пользователя, Fullscreen API.
- История розыгрышей, CSV текущей выборки участников и истории, транзакционный аудит, RLS.

Это первая реализация MVP. Подключённый hosted Supabase проверен по HTTP: Auth, публичное представление и screen RPC отвечают, закрытые таблицы и служебные RPC недоступны anon. Полный сценарий ещё не проверен: `register-participant` возвращает 404, а для развёртывания отсутствует авторизация CLI. Сборка, автоматические тесты интерфейса и проверки PostgreSQL прошли. Не считайте проверки с подменёнными сервисами заменой реального запуска мероприятия.

## Работа с уже включённым hosted Supabase без Docker

Укажите URL проекта и публичный ключ в `.env`, затем:

```powershell
npm.cmd run check:supabase
npm.cmd run dev
```

`check:supabase` выполняет проверки HTTP с публичным ключом, не изменяет данные и не выводит ключи или содержимое ответов. Проверяет Auth, public view, screen RPC, запрет anon на восемь внутренних таблиц и три служебные RPC, наличие Edge Function. Это проверка доступности и публичных прав; пустые ответы RLS сами по себе не доказывают безопасность всех строк.

Для развёртывания регистрации выполните вход Supabase CLI и команду:

```powershell
npm.cmd run supabase -- login
npm.cmd run deploy:registration
npm.cmd run check:supabase
```

`deploy:registration` берёт project ref из hosted URL в `.env` и развёртывает только `register-participant` через `--use-api`, без Docker, без сброса БД. Публичная регистрация использует `verify_jwt=false`. Настройте `ALLOWED_ORIGINS` для адреса frontend; по умолчанию разрешены localhost и 127.0.0.1 на порту 5173. См. [официальное описание развёртывания без Docker](https://supabase.com/changelog/33613-deploy-edge-functions-from-cli-without-needing-docker-import-files-outside-of-supabase-directory).

Для интеграционного сценария нужны существующие пользователи Auth с профилями `admin` и `host`. Добавьте в игнорируемый `.env` значения `EVENTDRAW_TEST_ADMIN_EMAIL`, `EVENTDRAW_TEST_ADMIN_PASSWORD`, `EVENTDRAW_TEST_HOST_EMAIL`, `EVENTDRAW_TEST_HOST_PASSWORD`, затем запустите:

```powershell
npm.cmd run test:integration
```

Сценарий проверяет реальные Auth/роли, конкурентные регистрации через Edge Function, повтор одного телефона, HTTP rate limit, Realtime, одновременный draw от admin и host, подтверждение, исключение победителя, отмену и Storage. Создаёт отдельное мероприятие со случайным slug, гостей и изображение; в `finally` удаляет только свои UUID/slug и путь изображения. Аудит сохраняется. Предпочтителен отдельный тестовый проект без Turnstile; при включённой серверной защите нужен ручной сценарий с действительным токеном. Скрипт ещё не проходил полный запуск на hosted проекте. Он не проверяет браузерную анимацию, QR и мобильную вёрстку.

## Локальный запуск

Нужны Node.js **22.12+** (рекомендуется 24) и Docker Desktop с Linux containers либо Podman. Supabase CLI установлен как devDependency. Версии зафиксированы в `package-lock.json`; `npm ci` воспроизводит установку. `.npmrc` размещает npm cache внутри проекта для ограниченных рабочих сред.

```powershell
npm ci
npm run supabase -- start
npm run supabase -- db reset
npm run supabase -- status
Copy-Item .env.example .env
```

В `.env` укажите URL и anon / publishable key из `supabase status`:

```dotenv
VITE_SUPABASE_URL=http://127.0.0.1:54321
VITE_SUPABASE_PUBLISHABLE_KEY=<public-key>
```

Секретные ключи, пароль БД и service-role key **никогда не должны иметь префикс `VITE_`**. Файлы `.env` игнорируются Git. Без настроек приложение показывает инструкцию подключения, без фиктивных данных и локального выбора победителя.

Запустите Edge Function в отдельном терминале:

```powershell
npm run supabase -- functions serve register-participant
```

И frontend:

```powershell
npm run dev
```

Откройте `http://127.0.0.1:5173`. Для локального теста QR с телефона потребуется доступный телефону адрес, запуск Vite с `--host 0.0.0.0`, доступный адрес Supabase вместо loopback и соответствующее значение `ALLOWED_ORIGINS`. В production QR автоматически использует origin опубликованного frontend.

Vite использует `--configLoader native`: конфигурацию читает Node, что также обходит ограничения чтения родительских каталогов при сборке в Windows sandbox. Здесь запуск dev-сервера потребовал выхода из sandbox для esbuild; в обычном терминале это ограничение отсутствует.

`supabase init` повторно выполнять не нужно: `supabase/config.toml` уже создан. `db reset` **сбрасывает локальную базу**, применяет все миграции и `seed.sql`. Для применения новых миграций без reset:

```powershell
npm run supabase -- migration up
```

## Первый администратор и ведущий

Самостоятельная регистрация сотрудников отключена в локальном `config.toml`. В hosted Supabase также отключите public signup в Auth settings.

1. Откройте локальный Studio `http://127.0.0.1:54323` или Dashboard вашего проекта.
2. В Auth → Users создайте пользователя с email и паролем, подтвердите email.
3. Выполните в SQL Editor, подставив UUID созданного пользователя:

```sql
insert into public.profiles(id, role, display_name)
values ('<auth-user-uuid>', 'admin', 'Организатор');
```

Для ведущего создайте другого пользователя и профиль с ролью `host`. Для пользователя с полными правами на назначенные мероприятия используйте роль `coadmin`:

```sql
insert into public.profiles(id, role, display_name)
values ('<auth-user-uuid>', 'coadmin', 'Соорганизатор');
```

Затем назначьте ведущего или соадминистратора в настройках нужного мероприятия. Роли не берутся из пользовательских метаданных и не могут быть повышены сотрудником. Пользователь без профиля не получает доступа к рабочему пространству. Управление профилями пока выполняется через доверенный SQL Editor, отдельного UI сотрудников нет.

| `202610100003_functions.sql` | Регистрация, draw engine, check-in, public screen RPC, rate limit |
| `202610100004_staff_stats.sql` | Агрегированные счётчики для ведущего без доступа к контактам |
| `202610100005_test_participants.sql` | Защищённое создание / удаление тестовых участников |
| `202610100006_check_in.sql` | Check-in по телефону, серверная нормализация, сохранение времени и аудита при повторных запросах |
| `202610100007_screen_controls.sql` | Управление ожиданием, паузой и отсчётом, защита текущего розыгрыша, аудит и серверный запрет запуска на паузе / до окончания отсчёта |
| `202610130001_event_access.sql` | Владение мероприятиями, явное назначение ведущих, RLS и RPC-проверки доступа ко всем данным мероприятия |
| `202610140001_event_coadmins.sql` | Роль соадминистратора и полный доступ к явно назначенным мероприятиям |

Таблицы: `profiles`, `events`, `event_staff`, `participants`, `event_ticket_counters`, `prizes`, `draws`, `event_screen_state`, `audit_logs`, `registration_rate_limits`. На каждой включён RLS.

Представления: `public_event_view`, `event_stats`, `prize_stats`, `confirmed_winners`. Публичное представление намеренно выполняется с правами владельца, но содержит только разрешённые колонки активных / завершённых мероприятий и явный фильтр; административные views используют `security_invoker` и RLS.

RPC:

| Функция | Кто вызывает |
| --- | --- |
| `register_participant` | Только service-role клиент Edge Function |
| `consume_registration_limit` | Только service-role клиент Edge Function |
| `create_event` | Только `admin`; владелец всегда определяется сервером по `auth.uid()` |
| `draw_winner`, `confirm_draw`, `cancel_draw` | Авторизованный `admin` / `host` |
| `set_screen_mode` | Авторизованный `admin` / `host`, только активное мероприятие без pending draw |
| `staff_check_in` | Авторизованный `admin` / `host`, возвращает данные без phone/email |
| `staff_check_in_by_phone` | Авторизованный `admin` / `host`, поиск по нормализованному телефону внутри мероприятия; результат без phone/email |
| `get_staff_stats` | Авторизованный `admin` / `host` |
| `get_public_screen` | Публично, только безопасная проекция |
| `manage_test_participants` | Только `admin` |

Все `SECURITY DEFINER` функции задают пустой `search_path`, используют квалифицированные имена и ограниченные `EXECUTE`. Сотруднические RPC дополнительно проверяют `auth.uid()` и роль.

RLS / grants:

- `anon`: только `public_event_view`, разрешённые строки `event_screen_state` и безопасный public screen RPC; нет доступа к контактам, прямой регистрации и таблице draws.
- `host`: чтение только явно назначенных мероприятий / призов / истории, собственный профиль, draw и check-in RPC; без изменения настроек, призов, профилей и чтения контактов / аудита.
- `coadmin`: полный административный доступ только к явно назначенным мероприятиям, включая настройки, участников, призы, аудит и назначение команды; без создания новых мероприятий.
- `admin`: управление только созданными им мероприятиями, их призами, контактами участников и аудитом; назначение ведущих и соадминистраторов через настройки мероприятия. Прямое изменение draws запрещено даже владельцу — только RPC.
- Таблицы счётчиков и rate limit закрыты от клиента. Сервисный ключ использует только Edge runtime.

Seed создаёт активное мероприятие `opening-2026`, пять видов призов и десять участников `is_test=true`. Они не участвуют в розыгрышах и публичном счётчике. Первый реальный билет seed-мероприятия — №011; в новом пустом мероприятии — №001. Удаление тестовых гостей не переиспользует номера.

## Архитектурные решения

- В ТЗ `draw_enabled` упомянут в алгоритме, но отсутствует в исходном перечне полей; поле добавлено в `events`.
- Билет выделяется увеличением отдельного счётчика внутри транзакции с блокировкой мероприятия. Телефон нормализуется в Edge Function и проверяется повторно SQL-функцией. Partial unique index гарантирует отсутствие дублей телефона; `NULL` допустим при необязательном телефоне.
- `draw_winner` блокирует мероприятие, получает снимок допустимых участников и выбирает одного через PostgreSQL `random()`. Frontend не выбирает победителя, в том числе offline. Единственный pending draw защищён partial unique index; повторный запрос того же приза возвращает тот же draw.
- В настройках мероприятия можно включить случайное назначение приза. Тогда `draw_winner` на сервере выбирает один из оставшихся экземпляров активных призов (каждый физический экземпляр имеет одинаковый шанс), а ведущему не нужно выбирать приз вручную.
- Подтверждение возможно после серверного срока анимации. Подтверждение / отмена повторного запроса идемпотентны; противоположное решение завершённого draw отклоняется. Отмена не расходует приз и не исключает гостя. Подтверждённые победы исключают гостя при `allow_multiple_wins=false`.
- Realtime публикует **только `event_screen_state`**: без телефонов, email и имён. Триггеры регистрации и изменений обновляют `updated_at`, поэтому один канал обновляет экран и админские данные. Public RPC возвращает только счётчик, текущий приз и разрешённые настройки имени / номера.
- `countdown_end` хранится в БД. После загрузки экран рассчитывает остаток с поправкой на часы сервера; по истечении срока отображает сохранённого победителя, даже если `mode` остаётся `drawing` до подтверждения. Это позволяет обойтись без браузерной записи состояния или фонового таймера на сервере.
- Повторная подписка и polling раз в 15 секунд восстанавливают данные после пропуска Realtime. Ведущий не может запускать розыгрыш при отсутствии соединения или ошибке загрузки. Browser receipt в sessionStorage служит только отображению ранее выданного билета; не участвует в доступе или выборе победителя.
- Check-in реализован защищённой RPC по номеру, как разрешено §42; отдельной `check-in` Edge Function нет. URL check-in доступен только сотрудникам.
- Призы отключаются, а участники деактивируются; история и ссылки на победителя сохраняются. Для тестовых участников предусмотрено явное удаление без переиспользования номеров.
- RPC, которые возвращают один результат, используют `jsonb` с явной формой ответа; это исключает неоднозначность массива / объекта при сериализации composite типов через PostgREST.
- CSV экспортирует текущую фильтрованную выборку / историю, экранирует кавычки и потенциальные spreadsheet formulas. Публичные формы не экспортируют контакты.

## Edge Function и secrets

`supabase/functions/register-participant/index.ts` проверяет JSON через Zod, нормализует телефон, применяет DB rate limit, при настройке проверяет Turnstile и вызывает закрытую RPC. Бизнес-проверки активного мероприятия, обязательных полей и дубля повторяются атомарно в PostgreSQL.

| ENV | Где | Назначение |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | Frontend `.env` | URL проекта |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Frontend `.env` | Public key либо локальный legacy anon key |
| `VITE_TURNSTILE_SITE_KEY` | Frontend `.env` | Опциональный публичный ключ виджета Cloudflare Turnstile |
| `SUPABASE_URL` | Edge runtime | Внедряется Supabase |
| `SB_SECRET_KEY` | Supabase Secrets | Новый secret key, если legacy service-role недоступен |
| `SUPABASE_SERVICE_ROLE_KEY` | Edge runtime | Legacy service-role fallback; локально внедряется CLI |
| `ALLOWED_ORIGINS` | Supabase Secrets | Origin frontend, несколько через запятую |
| `TURNSTILE_SECRET_KEY` | Supabase Secrets | Опциональная серверная anti-bot проверка |
| `EVENTDRAW_TEST_DATABASE_URL` | Только локальный тест | Адрес локальной БД для concurrency test |

Для локальных Edge secrets можно использовать игнорируемый `.env.functions` и передать `--env-file .env.functions` в `functions serve`. Не добавляйте этот файл в Git.

`verify_jwt=false` нужен публичной функции, включая запросы с publishable key. Регистрация не требует пользовательского JWT; доступ к service RPC закрыт grants. CORS ограничивает браузерные origin, но не заменяет антибот-защиту. Rate limit хранит SHA-256 ключ с серверным секретом, а не исходный IP: до 10 запросов в минуту на IP / мероприятие. Убедитесь, что ingress перезаписывает `x-forwarded-for`; без доверенного IP / с общим NAT возможны обход либо общие ограничения. Старые hashed ключи очищаются через сутки при следующих запросах.

Для включения Turnstile создайте виджет в Cloudflare и разрешите домен frontend. Укажите публичный `VITE_TURNSTILE_SITE_KEY` в frontend `.env`, пересоберите приложение и настройте соответствующий `TURNSTILE_SECRET_KEY` только в Supabase Secrets. Оба значения должны принадлежать одному виджету; серверный секрет никогда не получает префикс `VITE_`. При пустом публичном ключе виджет не загружается. При включённом серверном секрете Edge Function требует валидный токен независимо от состояния frontend.

Виджет загружается единожды через официальный скрипт с explicit rendering, ждёт готовности API, удаляется при уходе со страницы и не сохраняет токены в browser storage. Истечение токена, ошибка или тайм-аут проверки блокируют отправку и позволяют повторить проверку. После неудачного запроса регистрации виджет создаётся заново: Siteverify использует одноразовые токены. Поля формы сохраняются. См. [жизненный цикл виджета](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/) и [серверную проверку токенов](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

Проверки компонента и загрузчика используют подменённый Cloudflare API. Живую проверку проводите с настроенными ключами и доступным Supabase: получение билета, повторная регистрация, истечение токена, сбой загрузки скрипта и восстановление. Для локального сценария используйте [официальные тестовые ключи](https://developers.cloudflare.com/turnstile/troubleshooting/testing/); не переносите их в production.

## Production deployment

Создайте Supabase project, отключите public signup, настройте URL frontend в Auth. Затем:

```powershell
npm run supabase -- login
npm run supabase -- link --project-ref <project-ref>
npm run supabase -- db push
npm run supabase -- secrets set ALLOWED_ORIGINS=https://your-domain.example
npm run supabase -- functions deploy register-participant
```

При необходимости добавьте `SB_SECRET_KEY` через Supabase Secrets Dashboard; не передавайте секрет через общедоступные файлы / логи. Миграции сами создают bucket `event-assets`, настраивают policies и добавляют screen state в Realtime publication.

Production seed автоматически не создавайте: добавьте мероприятие и призы через UI. `seed.sql` предназначен для разработки.

Соберите frontend с production `VITE_` настройками:

```powershell
npm run build
```

Разместите `dist/` на static hosting. Настройте SPA fallback всех frontend routes на `index.html`. Supabase остаётся единственным backend. Bucket `event-assets` публичный и принимает PNG/JPEG/WebP до 5 МБ — загружайте туда только изображения для публичного показа.

## Ручной полный сценарий

1. Войдите как admin, создайте **новое пустое** мероприятие, в настройках выберите «Активно».
2. Добавьте приз, откройте QR и большой экран в другом окне.
3. Зарегистрируйте реального гостя: должен появиться №001. Повторите с вариантом того же телефона: получите №001 снова.
4. Убедитесь, что счётчик на большом экране изменился. При обязательном check-in отметьте присутствие сотрудником на `/event/:eventSlug/check-in`: выберите поиск по билету или телефону. Телефон допускает `87011234567`, `77011234567`, `+77011234567`, `8 (701) 123-45-67`. Повторная отметка сохраняет исходное время; действие «Отменить отметку присутствия» снимает отметку и очищает время. Доступ только для `admin` / `host`.
5. Войдите ведущим, выберите приз и запустите розыгрыш. Экран покажет анимацию и сохранённого сервером победителя.
6. Подтвердите: история станет confirmed, остаток уменьшится. При запрете повторного выигрыша гость больше не должен участвовать.
7. Добавьте второго реального гостя. Проверьте отмену отсутствующего победителя и повторный розыгрыш без расходования отменённого приза.
8. Перезагрузите / отключите сеть / восстановите связь в окне экрана и ведущего; данные должны восстановиться из БД, offline запуск должен быть запрещён.
9. Проверьте телефон, планшет и desktop, звук после нажатия, fullscreen, QR PNG и CSV.

## Продолжение этапа 11 — надёжность

Исправлены гонки смены сессии: выход немедленно сбрасывает профиль, а запоздавшие ответы загрузки профиля и первоначального чтения сессии не заменяют новое состояние. Ошибка запроса профиля снимает индикатор загрузки и блокирует доступ.

Повторный вызов действия до следующего React-render блокируется синхронно через ref; после успеха или ошибки действие снова доступно. Для данных мероприятия, призов и истории добавлена сверка с БД каждые 15 секунд в активной вкладке, чтобы панель ведущего восстанавливалась при потере Realtime-уведомления. При смене мероприятия статус соединения сбрасывается, а offline сохраняется при запоздалых callbacks.

Регрессионные тесты покрывают повторный запуск, повтор после ошибки, гонки авторизации, offline и смену Realtime-подписки. Проверки с подменёнными сервисами не заменяют интеграционный запуск Supabase.

## Продолжение этапов 9–11 — управление большим экраном

В панели ведущего доступны «Экран ожидания», «Пауза» и обратный отсчёт от 1 до 600 секунд. Команды сохраняются через `set_screen_mode` в PostgreSQL, передаются экрану существующей Realtime-подпиской и восстанавливаются после перезагрузки. Новые таблицы, buckets и ENV не нужны.

Отсчёт использует серверный `countdown_end`. После его завершения экран ждёт нажатия «Начать розыгрыш» ведущим: автоматического выбора победителя в браузере нет. Пауза запрещает новый розыгрыш; для продолжения выберите «Экран ожидания» или запустите отсчёт. Ожидание скрывает прошлый результат, сохраняя историю розыгрышей.

Смена режима блокируется при незавершённом розыгрыше. RPC использует ту же блокировку мероприятия, что draw / confirm / cancel; команда записывается в аудит в одной транзакции. Сервер также запрещает создание draw на паузе и до окончания отсчёта. Большой экран показывает паузу и отсчёт без старого победителя и праздничных эффектов.

Проверено: `npm.cmd test` — 38 тестов; `npm.cmd run test:db` — 23 проверки PostgreSQL через PGlite; `npm.cmd run build` — успешная production-сборка. Проверки охватывают права вызова, валидацию длительности, аудит, запрет скрытия pending draw, серверные ограничения запуска и отображение режимов. Полный Supabase / Realtime / Auth сценарий и конкуренция соединений ещё требуют интеграционного запуска.

Чтобы применить новую миграцию к запущенному локальному Supabase без сброса данных:

```powershell
npm.cmd run supabase -- migration up
```

## Тестовый розыгрыш — репетиция

Примените миграцию `supabase/migrations/202610100009_rehearsal_mode.sql` к hosted проекту целиком через Supabase SQL Editor → New query → Run. Либо примените новые миграции через CLI после подключения проекта (`supabase db push`). Edge Function менять не требуется.

1. В разделе «Участники» добавьте тестовых гостей кнопкой «Добавить тестовых».
2. Откройте панель ведущего и включите «Тестовый розыгрыш».
3. Выберите приз и нажмите «Начать тестовый розыгрыш». Подтверждение и отмена работают как обычно.
4. Завершите текущий розыгрыш и выключите переключатель для возврата к основному мероприятию.

В репетиции сервер выбирает только активных участников с `is_test=true`, без обязательного check-in. Реальные участники не участвуют. Настройка повторного выигрыша продолжает действовать, поэтому для повторных репетиций можно добавить тестовых гостей или включить «Разрешить повторный выигрыш». После репетиции верните нужную настройку для настоящего мероприятия.

Режим сохраняется в `event_screen_state.rehearsal_mode`; каждый draw получает неизменяемую клиентом отметку `is_test`. Тестовые подтверждения не расходуют и не резервируют призы, не включаются в основной список победителей и статистику. Можно репетировать даже с призом, уже выданным реальным победителям. В истории и CSV тестовые результаты помечены отдельно. Большой экран показывает «Репетиция», скрывает QR приглашения и восстанавливает режим из БД после перезагрузки. Смена режима сбрасывает старый результат на экране, запрещена при pending draw и записывается в аудит; права есть у admin/host, у anon их нет.

Если ранее вручную установили тестовым гостям `is_test=false`, они считаются обычными участниками. Для репетиции добавьте новых тестовых гостей; режим не меняет существующие флаги автоматически.
